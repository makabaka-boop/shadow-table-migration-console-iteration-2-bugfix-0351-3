# SQLite 影子表字段迁移与历史版本恢复

本项目包含：

- `frontend/`：React + Vite 页面，配置有限字段映射并展示预演失败行、源表修订号、**正式表代际**、正式表和只读历史版本；可在历史页对指定版本做**恢复预演**并确认恢复。
- `backend/`：FastAPI + SQLite 服务，复制到影子表、逐行校验、乐观修订号/代际提交、同一事务切换正式表并保留只读旧版，以及从历史版本预演并恢复正式表。

## 支持的字段映射

- `copy`：复制旧表字段。
- `trim`：去除字符串首尾空白。
- `decimal_int`：仅接受十进制整数文本，并限制在 SQLite 有符号 64 位整数范围内。
- `constant`：写入常量；目标整数字段必须提供整数常量。

目标字段为 `id`、`code`、`label`，正式表还保留 `legacy_id`。新表约束包括：非空、整数范围、`id`、`code`、`legacy_id` 唯一。

## 代际（formal table generation）

`revision_meta` 中有两个单调计数器：

- `legacy_records` 源表修订号：旧表任意插入、更新、删除都会 +1。
- `records` 正式表代际：初始为 0（尚无正式表）；**每一笔真正替换正式表的事务（字段迁移提交、恢复确认）在同一事务内 +1**。

字段迁移预演在服务端同时记录所见源表修订号与正式表代际；恢复预演记录所见正式表代际与来源历史版本。提交时以预演时的代际裁决，客户端提交字段保持兼容（`records_generation` 可省略），服务端保存的代际始终是最终依据。

## 恢复预演与确认

- `POST /api/restores/preview`，入参 `{"version_id": N, "selected_legacy_ids": 可选}`：
  - 从指定**已封存只读**历史版本复制内容，生成带最终约束（`PRIMARY KEY`、`NOT NULL`、`UNIQUE`）的候选表 `records_restore_candidate_<preview_id>`；带 `selected_legacy_ids` 时仅选中实体取自历史，未选中的当前实体原样并入候选。
  - 返回复核信息：候选行数、来源版本（版本号、种类、内容代际、行数）、与当前正式表的差异（候选新增 / 移除 / 字段变化，明细最多 200 条）。
  - 预演全程在独立事务中完成，**不改写任何记录、不封存、不切换、不推进代际**。
- `POST /api/restores/commit`，入参 `{"preview_id": ..., "records_generation": 可选}`：
  1. `BEGIN IMMEDIATE` 后重新校验预览存在、代际未变、候选存在且内容与封存历史逐行一致。
  2. 在**同一事务内**：插入恢复台账 → 把当前正式表完整复制为新的只读历史版本并封存锁定 → `DROP TABLE records` + `ALTER TABLE 候选 RENAME TO records` → 正式表代际 +1 → 作废全部存量预演与影子/候选表。
  - 代际过期（迁移或另一次恢复已落地）返回 `409 stale_preview`；约束失败、故障注入或任何异常都会整体回滚，失败预演立即作废，不可重复提交。

## 一致性说明

- 字段迁移预演在独立事务中创建带 `preview_id` 的影子表；约束失败或复制中断会回滚，不触碰正式表。
- 迁移提交必须携带预演返回的 `source_revision`（`records_generation` 可选，服务端代际为准）。提交事务使用 `BEGIN IMMEDIATE`，若预演后源表发生任何插入、更新或删除，返回 `409 stale_preview`；**若正式表代际变化（交错的恢复或更新的迁移提交落地），旧预演同样失效**，从而杜绝旧迁移提交覆盖刚恢复的内容。
- 每次成功替换正式表后，服务端在同一事务作废所有未提交的迁移/恢复预演并删除其影子/候选表。
- 提交/恢复时先复制旧正式表到历史版本，行数核对一致后再锁定封存，然后构建/切换带最终约束的新表。
- 正式表切换使用同一 SQLite 事务中的 `DROP TABLE records` 与 `ALTER TABLE ... RENAME TO records`。SQLite DDL 可事务回滚，因此复制中断、约束失败或切换失败都不会留下一半新一半旧的正式表、孤立历史版本或恢复台账。
- 历史版本元数据和行数据均通过 SQLite trigger 拒绝更新、删除或锁定后插入；恢复产生的封存版本与迁移产生的一视同仁。
- 历史版本 `version_id` 使用独立 AUTOINCREMENT 序列（迁移与恢复都在同一条版本线上），与 `migration_id`/`restore_id` 解耦。

## 测试

```bash
cd backend
PYTHONPATH=. python3 -m pytest tests -q
```

测试覆盖：

- trim、十进制解析、整数范围、非空、唯一、映射来源报告。
- 预演失败和复制中断后正式表/影子表状态。
- 迁移提交切换前故障注入的事务回滚。
- 两个客户端交错写入与真正并发写入下的修订号拒绝。
- 数据库修订号、正式表内容、历史版本内容及只读 trigger。
- 恢复预演只读、行数/约束复核、与当前正式表差异（新增/移除/字段变化）。
- **字段迁移与恢复交错**：先做的迁移预演在恢复落地后无法提交覆盖，重新预演后可继续；恢复预演撞上迁移提交也被拒绝。
- **两次恢复竞争**：两个同代际恢复预演在真实线程下同时提交，恰好一个成功，另一个 `409` 且回滚干净、不可重放。
- **重启后历史可查**：新进程重新打开同一数据库，代际、正式表、封存历史均可继续读取，并能继续恢复。
- 恢复切换前故障注入的整体事务回滚（无半张正式表、无孤立版本/台账、无残留候选表）。
- 恢复台账外键、恢复产物版本同样只读、可从恢复产物继续恢复。
- 旧客户端省略 `records_generation` 仍可提交；客户端伪造代际无法通过校验。


## 部分历史恢复
恢复预演可带 selected_legacy_ids，以稳定的 legacy_id 选择历史中的实体。
仅选中实体恢复到来源版本，未选中的当前实体原样保留；最终正式表仍须满足完整约束。
预演描述完整候选表与完整差异，提交封存整个旧正式表，绑定代际，失败不留下候选切换或孤立历史。
全量恢复及旧迁移预演仍兼容。字段相同但 id 与 legacy_id 不同的行不得被误选。
